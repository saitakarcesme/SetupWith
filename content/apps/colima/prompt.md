# Colima setup prompt

Set up Colima from the official abiosoft/colima project and installation guide (https://colima.run/docs/installation/). Detect macOS or Linux, CPU architecture, virtualization support, package managers, free disk and memory, existing Colima profiles, Lima instances, container clients, and active Docker and Kubernetes contexts. Install a stable packaged release through Homebrew, MacPorts, Nix, Mise, or the documented binary route; do not select Homebrew HEAD unless the user explicitly requests an unreleased build.

Before starting a profile, list its status and inspect its configuration without editing it. Explain that Colima creates a Lima virtual machine and that the default profile allocates CPU, memory, expandable virtual disk, networking, mounts, and a chosen Docker, containerd, or Incus runtime. Preserve every profile, VM disk, snapshot, image, container, volume, Kubernetes workload, kubeconfig entry, Docker context, SSH key, mount, port-forward rule, model cache, and existing configuration. Apply only the requested runtime, VM type, resource limits, or Kubernetes setting. Never silently reuse or resize an existing profile.

Ask before creating or starting a VM, reserving resources, increasing disk size, mounting host directories, forwarding ports, installing Docker, nerdctl, kubectl, Incus, krunkit, or Rosetta support, enabling Kubernetes, downloading images or AI models, or changing active client contexts. Do not switch an established profile's runtime, shrink a disk, expose a forwarded port beyond loopback, install a PATH alias, grant GPU access, or run `colima delete` without a separate impact preview and approval. Treat stop, reset, and delete as different operations; deletion must never be part of an automatic rollback.

Verify the Colima version and package provenance, then use `colima list`, `colima status`, and configuration inspection to report profile name, architecture, VM type, runtime, CPUs, memory, disk, Kubernetes state, mounts, and addresses. If creation was approved, start only a new named disposable profile and confirm client context selection without pulling an image or creating a workload. Prove pre-existing profiles, contexts, containers, volumes, cluster data, and files are unchanged. Roll back by stopping and removing only the setup-created profile after explicit approval and restoring the prior Docker and kubeconfig contexts.
