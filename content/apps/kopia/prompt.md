# Kopia setup prompt

Set up Kopia from its official installation documentation and signed release channel (https://kopia.io/docs/installation/). Detect Windows, macOS, or Linux, architecture, package managers, existing `kopia` and KopiaUI installations, connected repository configuration, scheduled jobs, services, and storage mounts without reading credentials. Distinguish CLI, desktop KopiaUI, web UI/server, and container deployment. Prefer the stable channel and verify the release checksum plus Kopia builder signature; do not select testing, unstable, source, or server mode unless explicitly requested.

Install only the approved CLI or desktop variant. Preserve repository configuration, encryption parameters, repository format, passwords, cloud credentials, caches, logs, policies, snapshot manifests, maintenance ownership, schedules, services, mounted snapshots, source data, and restore destinations. Never create or connect a repository during installation. Before later repository work, show provider, path or endpoint, new versus existing status, expected capacity, encryption and hashing defaults, username/hostname identity, and whether other clients share it. Repository format choices and password recovery consequences must be explained before creation.

The repository password encrypts all backup data and cannot be recovered if lost. Use only the opaque `secret://kopia/password` reference through a secure interactive prompt or permission-restricted secret provider; never place it in a command, environment dump, shell history, compose file, log, or committed configuration. Ask separately before accessing cloud or NAS credentials, selecting snapshot sources, scheduling backups, changing retention, running maintenance, deleting snapshots or content, mounting a snapshot, starting a server, exposing a port, disabling TLS or CSRF checks, or restoring files. Never make a repository's sole copy on the source disk.

Verify package signature, version, executable/UI paths, configuration permissions, processes, services, listeners, and absence of repository connections. Use help and version commands only; do not create a test repository with a throwaway password because that does not validate recovery. If a repository is later approved, require a documented password-backup location and perform read-only status plus snapshot listing before any write. A restore test must target a new empty directory and compare hashes without overwriting originals. Roll back only setup-installed binaries, services, and configuration, preserving repositories, snapshots, caches, credentials, policies, schedules, and source files.
