# kind setup prompt

Codex, inspect the OS, architecture, shell, existing `kind` and `kubectl` binaries, Docker or Podman availability, current kind clusters, kubeconfig, and available CPU, memory, and disk. Install the official kind binary through Homebrew on macOS, the signed release binary on Linux, or `winget install Kubernetes.kind` on Windows when supported. Ask before administrator access, installing or starting a container engine, creating or deleting clusters, binding host ports, changing firewall rules, or overwriting kubeconfig entries. Preserve all existing kind clusters, node containers, local images, and kubeconfig contexts. Configure only `cluster_name`, `node_count`, `kubernetes_version`, and `container_runtime` when supplied. Validate that the requested node image exists and matches kind’s documented format; do not invent a Kubernetes version or pull large images without approval. Generate a temporary cluster config rather than overwriting user files. Verify `kind version`, runtime connectivity, cluster creation, `kubectl cluster-info`, node readiness, and system pods. Use a uniquely named disposable test cluster if no persistent cluster was requested. Rollback deletes only the cluster created in this run, restores kubeconfig backups, and removes only the installed kind binary. Finish with a structured summary of runtime, image, cluster name, nodes, verification, approvals, and rollback.
