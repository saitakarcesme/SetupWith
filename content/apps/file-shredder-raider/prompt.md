# File Shredder setup prompt

Set up File Shredder from its official repository and verified Flathub listing (https://apps.gnome.org/Raider/). Inventory Linux architecture, Flatpak scopes, existing package and data paths, declared filesystem access and broad storage classes—rotational, SSD/NVMe, removable, network or virtual—without enumerating filenames, mounting media or opening user data. Install stable `com.github.ADBeveridge.Raider` from verified Flathub in the existing ownership scope. Do not compile from source, launch the app, select a file, grant extra filesystem access, empty trash, run an overwrite or perform any deletion during setup.

Preserve every user file, directory, link, mount, snapshot, backup, trash entry, cloud version, cache and application record. File Shredder performs intentionally destructive work; installation is never authorization to destroy data. A future request must identify one exact canonical file, its owner, business purpose, retention status and deletion authority. Reject directories, wildcards, unresolved symlinks, hard-linked content, paths outside the approved mount, active files and targets covered by legal hold. Require a second human confirmation after showing identity, size, inode/link count and irreversibility.

Overwriting a pathname is not a universal proof of erasure. SSD/NVMe and flash wear levelling, controller remapping, TRIM, copy-on-write filesystems, snapshots, journals, deduplication, sparse/reflinked extents, virtual disks and network storage can retain other physical or logical copies. Cloud sync, backups, thumbnails, indexes and recipient devices require separate owner-approved lifecycle actions. State these limits plainly; never certify forensic sanitization from application success alone. For strong retirement assurance, evaluate encryption-key destruction or the storage vendor's authenticated erase process against the actual threat model.

Before any approved destruction capture non-content metadata and approval evidence to a protected audit location, confirm backups are intentionally out of scope or separately governed, close writers and establish failure handling. Never create a test file in a user directory merely to demonstrate deletion. Verify File Shredder provenance, app ID, origin, commit, runtime, executable, files and permissions offline. Prove no path resolution, file read, portal grant, overwrite, unlink, TRIM, trash, snapshot, sync, log or filesystem state changed. On installation failure, rollback only the new File Shredder ref in its original scope; destroyed data has no application-level rollback, so no destruction may occur as part of verification.
