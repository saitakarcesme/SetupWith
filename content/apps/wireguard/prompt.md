# WireGuard setup prompt

Codex, inspect the OS, architecture, shell, existing WireGuard tools, kernel or userspace support, interfaces, routes, DNS configuration, service units, and firewall state before making changes. On Linux prefer the distribution’s official `wireguard-tools` package and native kernel support; on macOS or Windows use the official WireGuard application. Ask before administrator access, installing drivers, creating interfaces, enabling services, changing routes, DNS, ports, or firewall rules, importing tunnels, or overwriting configuration. Preserve all existing tunnel files, keys, routes, and service state. Configure only `interface_name`, `listen_port`, `address_range`, and `dns_server` when supplied. Use `secret://provider/WIREGUARD_PRIVATE_KEY` and `secret://provider/WIREGUARD_PRESHARED_KEY` only through protected files or secure runtime injection with strict permissions; never print, echo, log, or expose them in process arguments. Do not bring the interface up until peer endpoints and routing impact are approved. Verify `wg --version`, configuration syntax, file permissions, interface creation in a non-connected or test namespace when possible, and route conflict checks. Rollback disables only the created interface, restores DNS and routes, removes created service files, and preserves user configs. Finish with a structured summary of tooling, interface, addresses, DNS, port, activation state, verification, approvals, and rollback.
