# Secrets setup prompt

Set up Secrets from its official GNOME project and verified Flathub listing (https://apps.gnome.org/Secrets/). Inventory Linux architecture, Flatpak scopes, existing package and data paths, KeePass database count, aggregate encrypted-file size, storage and sync locations, backup age, lock policy, clipboard-history exposure, and master-password or key-file reference presence without listing filenames, groups, entry titles, usernames, URLs, notes, attachments, passwords, key material, or database headers. Install stable `org.gnome.World.Secrets` from verified Flathub in the existing ownership scope. Do not compile from source, launch Secrets, open or unlock a database, create a vault, prompt for credentials, read clipboard history, import records, or change encrypted files during setup.

Preserve every KeePass file byte-for-byte, including ownership, permissions, timestamps where practical, backups, sync versions, file locks, recycle state, attachments, custom fields and existing unlock factors. A master password cannot be recovered from the database; a lost key file can make the vault permanently inaccessible. Keep only secret references in setup records. Never print, test, migrate, copy, weaken, or replace a password or key file, and never infer that successful application installation proves a database can be recovered.

Before any later database creation or write, require the exact destination, owner, filesystem and backup protections, sync behavior, KeePass format, key-derivation parameters, compatibility target, atomic-write strategy, lock handling and conflict recovery. Benchmark derivation settings only against an empty disposable database with explicit approval; do not benchmark the user's vault. Review clipboard clearing, clipboard managers, screen capture, accessibility access, auto-lock on idle, suspend, logout and failed unlock behavior before exposing a real entry. Imports, exports and attachments require a separate field-level preview with redaction and a recoverable backup.

Verify app provenance, app ID, origin, commit, runtime, executable, files and sandbox permissions offline. Record whether the sandbox can reach user files, portals, clipboard, secrets services and biometric interfaces without exercising those capabilities. Prove no vault was opened, header parsed, credential requested, clipboard touched, authentication attempted, database created or modified, backup rotated, sync conflict triggered, or notification shown. On failure, rollback only the new Secrets ref in its original scope; preserve shared runtimes, remotes, overrides, databases, backups, key files, sync state and secret references.
