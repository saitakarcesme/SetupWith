# Pika Backup setup prompt

Set up Pika Backup from its official GNOME project and verified Flathub listing (https://apps.gnome.org/PikaBackup/). Inventory Linux architecture, Flatpak scopes, existing Pika Backup package and data paths, Borg repository count and ownership, local or remote destinations, source-root count, schedule state, exclusion policy, secret-store boundary and available capacity without opening archives, printing paths or reading passphrases. Install stable `org.gnome.World.PikaBackup` from verified Flathub in the existing ownership scope. Do not compile Borg or Pika Backup, launch the app, attach a drive, contact an SSH host, create or upgrade a repository, unlock an archive or run a backup during setup.

Preserve every repository URL, Borg ID, encryption mode, archive, lock, key, passphrase reference, source selection, exclusion, schedule, retention rule and notification setting. Repository names and file paths can expose identities and sensitive projects; redact them from diagnostics. Never assume an existing Borg repository is disposable or owned exclusively by Pika Backup. Do not break a lock, migrate formats, prune archives, compact segments or repair data without a separately reviewed maintenance plan and a second verified copy.

Before any future repository connection show destination type, owner, exact host identity, pinned SSH host key, TLS or SSH transport, credential source, repository version, free-space estimate and concurrent-writer policy. Encryption protects archive contents only while its key and passphrase remain recoverable; require an approved offline key-recovery plan before enabling unattended schedules. Exclusions must be reviewed against hidden files, application state, mount boundaries and symlinks. Pika Backup targets personal files and is not a complete system-recovery image.

A green backup result is not proof of recovery. Define a non-destructive verification that checks repository integrity within resource limits, lists archive metadata without exposing filenames, restores a small approved sample to a new protected directory, compares hashes and removes nothing automatically. Keep schedules and background access unchanged until that recovery drill passes. Verify provenance, app ID, origin, commit, runtime, executable, bundled Borg version, files and permissions offline. Prove no drive mount, secret access, network connection, repository lock, archive, schedule, prune, compact, restore, notification or filesystem state changed. On failure, rollback only the new Pika Backup ref in its original scope; preserve runtimes, remotes, overrides, repositories, keys and all backup data.
