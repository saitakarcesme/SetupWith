# Vaultwarden setup prompt

Codex, inspect the OS, architecture, shell, Docker or Podman availability, existing Vaultwarden deployment, data volume, database, attachments, environment files, reverse proxy, and occupied ports. Prefer the official `vaultwarden/server` container image with a persistent `/data` mount; use a native binary only on a supported host when containers are unsuitable. Ask before administrator access, installing container tooling, starting services, exposing ports, changing firewall rules, opening a browser, enabling registrations, or overwriting environment files. Preserve the database, attachments, RSA keys, sends, icon cache, and backups. Configure only `domain_name`, `server_port`, `data_directory`, and `signups_allowed` when supplied. Inject `secret://provider/ADMIN_TOKEN`, `secret://provider/DATABASE_URL`, and `secret://provider/SMTP_PASSWORD` through protected runtime secrets; never print, echo, log, or commit values. Default registrations to their existing state and keep the service localhost-bound until TLS and proxy settings are approved. Verify image identity, persistent volume access, database health, `/alive` or equivalent readiness, admin endpoint protection, and web vault loading without creating a real vault. Rollback removes only created containers and manifests, restores backups, and retains all data unless deletion is authorized. Finish with a structured summary of runtime, storage, domain, registration state, authentication, verification, approvals, and rollback.
