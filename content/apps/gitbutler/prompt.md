# GitButler setup prompt

Set up GitButler from its official download source and repository (https://gitbutler.com/downloads). Detect Windows, macOS, or Linux, architecture, existing desktop and `but` CLI installations, system Git version, global and repository Git configuration, credential helpers, SSH agents, signing setup, repositories previously registered with GitButler, and application data without reading private keys or tokens. Install only the signed stable desktop package; treat CLI installation as a separate choice and download its installer for inspection instead of piping it directly into a shell.

Launch GitButler without adding or cloning a repository. Preserve every working tree, index, HEAD, branch, ref, reflog, stash, worktree, submodule, untracked and ignored file, hook, remote, upstream, credential helper, signing key configuration, GitButler project registry, virtual branch, target branch, and application database. Repository onboarding and `but setup` are mutations: they can register the project, select a production target, and switch to GitButler's workspace branch. Show exact refs, configuration and file effects before requesting separate approval.

Never test credentials during setup because the documented check pushes and deletes a temporary remote branch. Stop before fetching, applying or unapplying a branch, assigning hunks, committing, editing history, rebasing, squashing, splitting, updating from upstream, pushing, force-pushing, opening a pull request, or landing directly to the target branch. Direct landing may bypass review and CI, while CLI push can force by default, so always preview explicit source and destination commit IDs. Do not authorize GitHub, add a PAT, upload a signing key, alter signing fallback settings, or send diffs to AI message generation.

Verify publisher, version, executable and data paths, then inspect settings offline. Use a setup-created disposable Git repository with no remote and no user files only if UI verification is necessary; record its refs and hashes before and after, and remove only that disposable project registration. Confirm no production repository was scanned, no background fetch or network connection occurred, and no Git configuration, credential, ref, index, worktree, hook, or application database entry outside the test changed. Roll back binaries and setup-owned settings only; preserve GitButler metadata and repositories unless teardown effects are explicitly reviewed.
