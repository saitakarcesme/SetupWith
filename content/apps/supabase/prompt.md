# Supabase setup prompt

Codex, first inspect the OS, architecture, shell, Docker-compatible runtime, existing Supabase CLI, local project configuration, containers, volumes, database state, and occupied ports. Prefer the official Supabase CLI through Homebrew on macOS or Linux, npm only in an existing managed Node environment, and `scoop` or the official supported Windows method; use the CLI’s documented local Docker stack rather than assembling services manually. Ask before administrator access, installing or starting Docker, initializing a project, creating containers, exposing ports, changing firewall rules, opening Studio in a browser, or overwriting `supabase/config.toml`. Preserve migrations, seed files, local volumes, functions, storage objects, and project settings. Configure only `site_url`, `api_external_url`, `studio_port`, and `database_port` when supplied. Inject `secret://provider/POSTGRES_PASSWORD`, `secret://provider/JWT_SECRET`, `secret://provider/ANON_KEY`, and `secret://provider/SERVICE_ROLE_KEY` through protected local environment handling; never print, log, or commit values. Verify `supabase --version`, config validity, container health, database readiness, API health, and Studio reachability without signing into a cloud project. Rollback stops and removes only newly created local services, restores config backups, and retains volumes unless deletion is approved. Finish with a structured summary of CLI source, project path, ports, services, verification, approvals, and rollback.
