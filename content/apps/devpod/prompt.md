# DevPod setup prompt

Set up DevPod from its official installation guide (https://devpod.sh/docs/getting-started/install). Detect Windows, macOS, or Linux, architecture, package managers, container runtimes, SSH and Kubernetes clients, cloud CLIs, existing DevPod desktop or CLI installation, contexts, providers, workspaces, machines, IDE preferences, configuration, caches, volumes, and credentials. Install only the signed stable desktop package or checksummed CLI using the documented method for the platform. Do not add or select a provider, authenticate, create a context, open a repository, or start a workspace during installation.

Preserve every provider definition and option, workspace and machine record, Dev Container configuration, local clone, volume, cache, IDE association, SSH or Kubernetes context, cloud account, credential helper, dotfiles setting, and uncommitted file. Report existing resources read-only before proposing changes. A provider is an executable integration that can create, stop, and delete remote machines or containers; adding, updating, selecting, reusing, or removing one requires an exact command preview and separate approval. Never delete a provider while a workspace depends on it, and never infer that an apparently idle cloud machine is disposable.

Treat `devcontainer.json`, Features, images, entrypoints, lifecycle hooks, IDE extensions, and dotfiles bootstrap files as arbitrary code. Do not run `devpod up`, build, rebuild, prebuild, start, stop, delete, purge, or provider commands merely to verify setup. Before any later workspace action, pin the repository revision and image digest where possible, inspect Features plus hooks, show the provider, destination, forwarded ports, mounts, secrets, privileges, estimated cloud resources, and deletion scope. Dotfiles mode may clone a repository and automatically run `install.sh`, `bootstrap.sh`, `setup.sh`, or a custom script; keep it disabled until the repository and exact script are reviewed. Never print tokens, copy host credentials into a workspace, weaken SSH host checking, change the active Kubernetes context, expose a Docker socket, or grant privileged containers silently.

Verify the downloaded artifact, publisher or checksum, `devpod version`, resolved binary, desktop bundle, installation method, configuration path, and PATH precedence. Use only read-only listing commands that do not contact providers or start resources; if a listing might invoke a provider, stop and explain. Confirm no provider, context, workspace, machine, container, VM, volume, credential, dotfile, IDE, port, repository, or cloud resource changed. Roll back only the installed DevPod binary or application and setup-owned PATH entry, preserving all pre-existing DevPod state and remote resources.
